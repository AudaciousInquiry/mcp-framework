# Design

> **Status: all 11 decisions are approved.** Each was reviewed with the user one point at a time. Next: reconcile
> the specs touched by the two-file and shared-tools layout, then write `tasks.md`.

## Context

See `proposal.md` (Why) for the motivation and `specs/` for the requirements. This design explains how the
framework is built.

Constraints that shape the approach:

- The framework is extracted from two working servers that share one pattern: a launcher that starts a
  detached HTTP server, a server that exposes the tools, and a stdio bridge for clients that can only launch
  stdio programs. Both keep the launcher and the server in separate files.
- Node 22 or later, CommonJS, plain JavaScript with JSDoc, no build step (proposal, non-functional
  requirements).
- It must work on Windows as well as Linux and macOS. In particular, Windows never delivers `SIGTERM` to a
  handler, so a graceful stop cannot rely on signals.
- The package is public and self-contained, so nothing in it may refer to a private project.

## Goals / Non-Goals

**Goals:**

- An MCP author writes only what is specific to the MCP (its tools, defaults, and hooks). Everything about
  process lifecycle, transport, command line, configuration, and logging comes from the framework.
- The launcher stays light. Commands that only query or configure (`list`, `call`, `health`, `stop`, `init`)
  never load the author's tool code.
- A small public surface, so the semver contract stays small.

**Non-Goals:**

- Migrating the existing MCPs to the framework. That is a separate change.
- An in-process stdio mode that skips the daemon. A framework MCP always runs as daemon plus bridge.

## Decisions

### Decision 1: One entry point for the launcher

The launcher file calls a single function, `runLauncher(definition)`. It validates the definition at start-up
and fails with a clear message when a required field is missing. Everything else the framework does (daemon
control, bridge, command line, configuration, logging) is internal. The only other public exports are the
base class for the server (Decision 2), the logger factory, and the helpers for marking argument schemas,
such as the `x-cli: 'file'` marker.

```js
const { runLauncher } = require('mcp-framework');

runLauncher({
  defaultPort: 7561,
  serverScript: 'server.js',                 // optional, this is the default
  nodeArgs: ['--max-old-space-size=8192'],   // optional
  settings: z.object({ /* types for init */ }),
  // launcher-side hooks: default arguments for call, bridge start-up, init prompts
});
```

**Alternative considered:** export the pieces (start the daemon, create the bridge, create the command line)
and let each MCP wire them together. That is more flexible, but it recreates the copy-and-drift problem the
framework exists to remove, and it makes the semver surface much larger.

### Decision 2: Two files, a base class for the server, and a detached spawn

An MCP has two files, as both existing servers do.

- **Launcher** (`index.js` by convention): calls `runLauncher`. It handles the command line, starts and stops
  the daemon, and runs the stdio bridge. It does not load the tool code.
- **Server** (`server.js` by default): exports a class that extends the framework's `McpServerBase`, and
  starts it only when the file is run directly.

```js
const { McpServerBase } = require('mcp-framework');

class MyServer extends McpServerBase {
  async startup(config, log) { /* create long-lived resources; return the context */ }
  registerTools(server, context) { /* register the tools */ }
  async afterListening(context) { /* slow setup goes here */ }
  healthExtension(context) { /* extra health fields */ }
  async shutdown(context) { /* release resources */ }
}

module.exports = MyServer;
if (require.main === module) new MyServer().run();
```

`McpServerBase` carries the shared behavior: stateless HTTP on loopback, `/health`, port-in-use handling,
the process id file, the graceful `POST /shutdown` sequence, logging, and the fatal-error handlers. The author
overrides only what is specific to the MCP. Exporting the class without starting it lets tests load it
without starting a server.

Details:

- **Server file name:** the launcher definition names it in `serverScript`, relative to the launcher's
  directory, defaulting to `server.js`. It is not a user setting, because a user has no reason to run a
  different script and a configuration value that makes the launcher execute an arbitrary path is a hazard.
  The launcher checks that the file exists and fails with a clear message when it does not.
- **Name and version:** the framework reads both from the MCP's own `package.json`, so they cannot drift from
  the package.
- **Starting the server:** the launcher uses detached `spawn` of `process.execPath` with the optional
  `nodeArgs` placed before the script path, the server's standard output ignored and its standard error
  inherited from the launcher (so the server's logging configuration decides where output goes), and `unref`
  so the server outlives the launcher. Node ignores a runtime option such as the heap limit if it comes after
  the script path, which is why `nodeArgs` goes first.

**Alternatives considered:**

- *One file that re-runs itself with an internal flag.* Less to write, but it depends on `process.argv[1]`
  being the real script, which a shim or `npx` can break, and it differs from the layout both existing
  servers already use.
- *`child_process.fork`.* It is `spawn` plus a message channel, and the channel is of no use because the
  server must outlive the launcher. It would need a `disconnect` and `unref`, it passes the launcher's own
  Node flags (such as a debugger flag) on to the server by default, and it would add a second way to learn
  that the server is up when polling `/health` is needed anyway.

### Decision 3: Dependencies

Three runtime dependencies, a few small pieces written in the framework, and everything else built in.

- `@modelcontextprotocol/sdk` (`^1.32`), a direct dependency. The framework owns the version it is tested
  against.
- `log4js` (`^6.9`), a direct dependency. It provides the daily rotation, size limit, backups, and levels that
  the diagnostics-logging spec describes, and the existing servers already use it with the same settings, so
  their log files keep the same shape. It is an approved exception to the maintenance rule (see below).
- `zod` (`^4.4`), a peer dependency. The SDK declares `zod` as a required peer as well. A peer means one copy of
  Zod is shared with the author's schemas; two copies would break the `.meta()` markers that argument typing
  reads.

Written in the framework:

- **The argument parser.** Node's `util.parseArgs` rejects `--since -7d` as ambiguous (only `--since=-7d`
  works), and the argument-mapping spec requires the first form, along with dotted names, `--no-name`, and its
  own quoting rules.
- **Date parsing.** The spec allows ISO forms and a short list of relative words and forbids natural language,
  which a date library would add back.
- **Comma and quote splitting**, which follows the spec's own quoting rules.
- **A thin logging module** that configures `log4js`: appenders, named loggers, the level override, and the
  standard error mirror. It is the only code that imports `log4js`.

Built in, no dependency: `node:http`, `child_process`, `readline/promises` for the `init` prompts, and
`node:test` for tests.

**Vetting.** `npm audit` on the SDK, `zod`, and `log4js` together reports no vulnerabilities of any severity.
The SDK (2026-10-23) and `zod` (2026-10-12) were released within the past 12 months. `log4js` has had no
release since 2023-03-08, which fails the 12-month rule; the user approved it as an exception on 2026-11-21.
The exception covers the maintenance criterion only, and the no-unfixable-CVE rule still applies. Licenses are
MIT (SDK, `zod`) and Apache-2.0 (`log4js`).

**Alternatives considered:**

- *`rotating-file-stream` with a small formatting layer of our own.* It passes every vetting check (released
  2026-11-11, no dependencies), but it replaces a working library with code we would have to write and test. It
  is the fallback if `log4js` ever develops a problem.
- *`pino-roll` and `winston-daily-rotate-file`.* Their last releases were 2025-10-06 and 2024-02-09, so they
  fail the same rule that `log4js` does, with no offsetting advantage.

### Decision 4: Tool schemas live in a shared file that the launcher reads locally

The command-line commands learn their types from the same code base that defines the tools, not from the
running server. A third small file, `tools.js` by convention, holds each tool's name, description, and Zod
schema, and no handlers. The launcher and the server both load it, and the server loads the rest of the tool
code separately.

```js
// tools.js, shared by the launcher and the server
const { defineTools } = require('mcp-framework');
module.exports = defineTools([
  { name: 'search', description: '...', inputSchema: z.object({ query: z.string() }) },
]);

// index.js: runLauncher({ defaultPort: 7561, tools: require('./tools'), settings: ... });
// server.js: this.register(server, require('./tools'), { search: async (args) => { ... } });
```

- **One source of truth.** The framework's `register` helper attaches handlers to the shared definitions by
  name, so the server cannot register a tool the file does not describe. The two cannot drift.
- **One converter.** It takes a JSON Schema and the raw command-line tokens and produces typed JSON. For
  `call` the schema comes from the shared tool definitions, converted with Zod 4's `z.toJSONSchema`. For
  `init` it comes from the launcher definition's `settings` schema plus the framework's own settings, and a
  setting with no declared type is typed from its default's value. The `.meta()` markers, such as
  `x-cli: 'file'`, are read from the same schemas.
- **The call itself still goes to the server over HTTP.** Only the schema lookup is local. As a result,
  `call --help <tool>`, argument errors such as an unknown name, and `list` all work with no server running.
- **Validation stays on the server.** Rules the schema cannot express, such as refinements, are checked by the
  server; the client only converts types.
- **Tools registered at run time.** A tool that is not in the shared file is unknown to the launcher. `call`
  still sends JSON arguments for it as before and rejects flag-style arguments with a clear message.

**Alternatives considered:**

- *The launcher asks the running server for its tool list over MCP.* It carries the same schemas the agents
  see, but it needs a running server for help and for argument errors, adds a round trip to every call, and
  duplicates what the shared file already provides.
- *A custom schema endpoint on the server.* One more endpoint to keep in step with the tool list, for no gain.
- *The launcher imports the whole server file.* It avoids the file split but makes the launcher load the tool
  code and its heavy dependencies, which Decision 2 avoids.

### Decision 5: How the HTTP server handles a request

**Structure.** The server uses plain `node:http`, with the SDK's stateless transport doing the MCP work. Three
routes exist: `POST /` carries MCP, `GET /health` reports health, and `POST /shutdown` begins a graceful stop.
Any other route gets a 404. `GET` and `DELETE` on `/` get a 405, because stateless mode has no streams to open
and no sessions to close.

**A fresh SDK server and transport for every MCP request, with no session id.** This is the SDK's documented
stateless pattern. The framework builds the server, calls the author's `registerTools(server, context)`,
connects, handles the request, and closes both when the response ends. Long-lived resources live in the
`context` returned by `startup`, shared across requests. `registerTools` therefore runs on every request and
must be cheap: it registers tools and never creates resources.

**Handler wrapping.** The `register` helper from Decision 4 wraps every handler. An exception becomes an
ordinary error result, not a failed request, and the stack goes to the log. Each call's start, duration and
outcome are logged. The wrapper is where the tool-error and tool-call-observability requirements live, so
authors cannot forget them.

**Who may call.** Binding to loopback keeps other machines out. It does not stop a web page open in the user's
browser from reaching `127.0.0.1`, for example through DNS rebinding. The MCP transport specification requires
servers to validate `Origin` and return 403 for an invalid one. Tools such as file writers, and the `/shutdown`
route, make this matter. The server therefore refuses, before any other handling:

- any request that carries an `Origin` header, with 403. Agents, the command line and the bridge never send
  one. Allowing loopback origins was rejected because a page served from `http://localhost:3000` could still
  fire the body-less `POST /shutdown`, which a browser sends without a preflight.
- any request whose `Host` is not `127.0.0.1`, `localhost` or `[::1]` on the server's own port, with 403. This
  stops DNS rebinding, where the browser believes the request is same-origin.

**No CORS.** The server sends no `Access-Control-*` headers. CORS only relaxes the browser's rules for reading
responses, and no web page should talk to this server. Omitting it is not protection on its own (simple
requests are still sent), which is why the Origin and Host checks do the work. The cost is that a browser-based
MCP client cannot connect directly; none is in scope, and browser tools that go through a local proxy send no
`Origin`. An `allowedOrigins` setting can be added later if a real need appears.

**Implementation.** About 20 lines on `node:http`. The SDK's Host-check helper is written for Express and has no
Origin check, so it is not used. A body size limit is applied to the JSON body before parsing. The default is 1 MB, set from the size
distribution of the files in the author's own index: 97% are under 1 MB, and the files over 1 MB that a tool
could receive inline were a handful of `md` files (the largest 1.64 MB, session text logs) and test or reference
`csv` data that tools take by path. An MCP raises it with `maxBodyBytes`, and the 413 message names that setting.

**Alternatives considered:**

- *Express or Hono for routing.* An extra dependency for three routes.
- *One shared SDK server and transport across requests.* It needs sessions, which the stateless default rules
  out; the SDK's stateless mode expects a fresh pair per request.
- *Rely on loopback binding alone.* It matches the source being extracted, but leaves the browser path open.
- *Allow loopback origins.* Rejected as above.

### Decision 6: Starting, stopping and checking the daemon

The mechanics follow the launcher the framework is extracted from, adjusted for the rules in the specs. Each point
was approved on its own.

**6.1 Health probe.** One `GET /health` to `127.0.0.1` with a 5 second timeout and no retries. A parsed body means
the server is up. A refused connection means nothing is listening. A connection that is accepted but gets no
answer means a server is there and busy, and the launcher reports it and leaves it running. The literal address
is used, never `localhost`, which can resolve to IPv6 first while the server listens on IPv4 only.

**6.2 Start: wait for an event, then ask once.** The launcher removes a stale process id file, spawns the server
(Decision 2), and waits for one of three events: the child exits (reported with its exit code), the process id
file appears (the server writes it only after binding), or the startup timeout passes (30 seconds by default,
`startupTimeoutMs`). When the file appears it sends one `/health` probe as in 6.1. At the timeout it checks the
file and probes once more, in case a file-watch event was missed, then reports the timeout, names the process id
and the log file, leaves the server running, and exits non-zero. There is no polling loop and no kill.

**6.3 Windows console window: dropped.** The server writes nothing to standard output, its standard error is
whatever the logging configuration sends there (6.9), and the launcher this is extracted from starts its server detached without `windowsHide` and has
shown no console-window problem in use. `windowsHide` is not used. (Node's documentation says a detached child on
Windows has its own console window; whether one is ever visible was not established by test, so this rests on
the observed behaviour above.)

**6.4 Simultaneous starts: no special handling.** Starts overlap rarely, since an agent is started and waited for
one at a time. The port-in-use handling from Decision 5 covers it: a second server that finds the port taken
reads `/health`, sees the base fields, and exits with status zero. There is no lock file. An exclusive-create
lock file (`O_EXCL`) and a held write lock were considered. Node can create a file exclusively, but cannot hold
it against deletion (its files are opened with permissive Windows sharing), and the port bind already does the
job without a stale-file case.

**6.5 Stop.** Only an explicit stop, restart, or replacement of an older version ends a server.

1. `POST /shutdown`, answered within 5 seconds.
2. If it answers, wait up to 30 seconds for the process to exit. That is longer than the server's 10 second drain.
3. If it does not answer, or does not exit in time, terminate the process, and force-kill it if it is still alive
   after 15 seconds.
4. Wait up to 5 seconds for the port to stop accepting connections, then remove the process id file.

The launcher reports whether the stop was graceful or killed. The timings are the ones in use today.

**6.6 The server's own shutdown.** The same sequence starts from `POST /shutdown`, SIGTERM or SIGINT: stop
accepting connections, let in-flight requests finish for `drainMs` (10 seconds by default), destroy the rest, run
the author's `shutdown` hook to completion, remove the process id file, and exit with status zero. A second
trigger is ignored. Uncaught exceptions and unhandled rejections log the stack trace and exit with status 1.
On Windows, `/shutdown` is the only way to run this sequence: a signal sent by another process with
`process.kill` ends the process without running its handler (tested for SIGTERM and SIGINT; SIGKILL can never
be caught on any system). The signal handlers still serve Linux, macOS, and Ctrl+C in a terminal.

**6.7 Process id file.** The server writes its process id after binding and removes it at shutdown. A launcher
uses the process id from `/health` when the server answers, and reads the file only when it does not. A file
whose process is not running is stale and is removed. No further guard is added against the operating system
reusing a process id, which is too unlikely to design around.

**6.8 Version compare.** A function of about eight lines compares major, minor and patch in order and ignores
any suffix, as the spec requires. The `semver` package was not used: it ranks a pre-release below its release,
which would change the approved behaviour, and Decision 3 keeps the dependency list short.

**6.9 Server output and the debug option.** The server's standard output is ignored, and its standard error is
always inherited from the launcher. The server's logging configuration, not the launcher, decides where output
goes: the logger writes to its configured file, and with the debug option it also writes to standard error,
which appears on the console the launcher was run from. A crash before the logger exists prints to the same
inherited standard error. The server ignores errors writing to standard error, so a closed terminal never stops
it. A start-up capture file owned by the launcher was rejected because it takes the choice of destination away
from the server's logging configuration.

Consequence, stated in the README: when the launcher's standard error is read through a pipe, for example by a
script or a tool that captures its output, the reader does not see the end of the output until the server
stops, because the server holds that pipe open. At a console there is nothing to wait for.

Tests claim only what they check: log lines are mirrored to a connected standard error; a closed standard error
is ignored; and lines appearing in a real terminal window is a manual step in the Windows release checklist.

**6.10 A bearer token for `/shutdown`.** Proposed by the user after the pull request review. At start the server
makes 32 random bytes (hex), keeps them in memory, and writes `{"pid": n, "token": "..."}` to the process id file
(mode 600 where the system honors it). `POST /shutdown` is refused with 401 unless `Authorization: Bearer <token>`
matches, compared in constant time; a new token is made at every start. Any local client that can read the file
can stop the server, which is the same audience as before but no longer includes a process that merely reaches the
port. The launcher reads the token from the file and sends it only when the file's pid equals the pid the `/health`
answer reported, so the token is never given to an unrelated listener, and it kills a process only when the file
names it (a review finding: `/health` alone could name any pid). A file holding a plain number from an older
version is read as a pid with no token. `/health` keeps its shape check, now requiring a whole-number pid above 1.

**Alternatives considered:** polling `/health` every 200 ms (replaced by waiting for the process id file); a
lock file for single instance; looking up the port's owner with `netstat` or `lsof`; `taskkill` or a tree-kill
library (not needed for one process with worker threads; a plugin that spawns its own children cleans them up in
`shutdown`).

### Decision 7: The stdio bridge

Each point was approved on its own.

**7.1 How the bridge learns the server is gone.** The SDK's HTTP client transport calls `onclose` only when the
bridge closes it itself, never when the server dies, and the server is stateless, so there is no standing
connection to lose. A bridge that waited for a close event, as the one this is extracted from does, would never
recover. The trigger is a failed forward instead. When forwarding a request fails at the connection level, the
bridge answers that request at once with an error response carrying its id, and starts one respawn, guarded by a
flag so that only one runs at a time. Requests that arrive during the respawn get the same immediate error.
Forwarding resumes when the server is healthy. A failed notification has no id and is only logged. One
consequence: when the server dies while the client is idle, the first call afterwards gets the error and the
next one succeeds. Retrying the failed request once after the restart was considered (it is safe when the
connection was refused, because nothing was delivered, and unsafe after a reset in mid-request) and left out for
now. It is worth revisiting once a real MCP has been moved onto the framework. That migration is a separate
change request, and ecfr-mcp, the simplest of the existing MCPs, is the proposed first one.

**7.2 What does the forwarding.** The SDK's HTTP client transport, which the source bridge also uses, with the
SDK's stdio server transport on the client side. A server reply can arrive as plain JSON or as an event
stream, and the transport handles both. It also accepts the 405 that stateless mode gives to a request for a
standing stream. The bridge adds no protocol logic.

**7.3 Which failures mean the server is gone.** Connection refused or reset: respawn. A connection that is
accepted but gets no answer: the server is busy, so reply with an error and do not respawn. An HTTP error
status such as 500, 413 or 403: the server is alive and said no, so reply with an error and do not respawn.
This is the same rule as the health probe in 6.1, so the bridge never starts a second server on a busy one.

**7.4 Keeping standard output clean.** In bridge mode the framework replaces `console.log`, `console.info` and
`console.debug` with writers to standard error before any author code runs, so a stray print in the start-up
hook or in plugin code cannot corrupt the protocol stream. The SDK's stdio transport writes to the real
standard output directly and is not affected.

**7.5 The rest of the bridge.** Already in the spec, with no further design: the bridge runs until the client
closes standard input and then exits with status zero without stopping the server; it makes sure a server is
running using the launcher's start path (6.1 and 6.2) and waits for it to be healthy, and on failure writes the
reason to standard error and exits non-zero without writing to standard output; and the start-up hook runs
once the server is healthy and again after each respawn.

**State a plugin needs per agent session.** The framework has no session concept. A plugin that must know who
is calling does that in
the start-up hook and keeps what it registers in its own storage. That is part of the migration, not of the
framework.

**Alternatives considered:** waiting for a close event from the transport (never fires, above); writing the
forwarding with plain `fetch` (needs event-stream parsing the SDK already does); relying on authors never to
print to standard output.

### Decision 8: Configuration file handling

Each point was approved on its own.

**8.1 Where it lives.** `~/.mcp/<name>/config.json`, where `<name>` is the MCP's `package.json` name. The data
directory, the process id file and the log file are in the same folder.

**8.2 Writing the file.** Two cases, both our own code with no library. Creating the file on first run uses the
exclusive-create flag (`wx`): if two processes try at once, one succeeds and the other gets `EEXIST`, ignores it
and reads the file. Saving over an existing file writes a temporary file in the same folder and renames it over
`config.json`, so a reader sees either the whole old file or the whole new one. A reader could in theory see a
new file a moment before its writer finishes; the file is a few hundred bytes written in one call, so this is
accepted.

**First run is written by the launcher side only.** The launcher, the bridge and the command-line commands write
the defaults when the file is missing. The server only reads: with no file it uses the defaults in memory and
creates only the data directory it needs. A user whose file holds a default that a later version changes keeps
the old value, because stored values win; the README says so.

**8.3 The save function.** One function that an implementer can call, which `init` also uses. With no argument it
stores the current configuration, including changes made in place. With a partial set of settings it merges
them into a copy, validates the copy, writes it, and only then updates the in-memory configuration, so a
rejected update changes nothing. The MCP may supply a function that validates or normalizes the configuration.
The framework promises no further plugin-facing save API: a launcher option that changes a setting is
written in that MCP's migration and calls this function.

**8.4 Merging.** Stored values are merged over the defaults with a small function of our own (about fifteen
lines). Nested objects merge key by key; arrays are replaced whole, since merging two lists would mean guessing
what the user meant; a stored `0`, `false` or `null` is a real value; unknown keys are kept and written back.

**8.5 Getting at the configuration.** There is no separate retrieval function and no hot reload; the server reads
its configuration once at start and a changed setting takes effect on restart. In the server, the object passed
to `startup` is also `this.config` on the base class, next to `this.log`. Each launcher hook receives one
framework-defined object, `ctx`, with `ctx.config` (the merged configuration, with the save function),
`ctx.client` (calls the server's tools, as the command line does) and `ctx.log`.

**Alternatives considered:** the server writing the file on first run (a race between processes); writing
defaults only when a user sets something, so that changed defaults reach everyone (rejected: first run writes the
defaults); the `write-file-atomic` package; merging arrays; a configuration retrieval function separate from
the hook object.

### Decision 9: Logging

Each point was approved on its own.

**9.1 What writes the log.** `log4js`, chosen in Decision 3, behind one thin internal module that is the only
code importing it. The file is `server.log` in the `logs` folder of the data directory. It rolls over daily and
at 10 MB and keeps 7 old files, the values in use today.

**9.2 The log level.** First match wins: the environment variable `<NAME>_LOG_LEVEL` (for `my-mcp`,
`MY_MCP_LOG_LEVEL`), then `log_level` in `config.json`, then the default `info`. The values are `trace`, `debug`,
`info`, `warn` and `error`, and an invalid value is an error naming the setting and the allowed values. Worker
threads work the level out the same way from the same environment and file, so nothing is passed between threads.

**9.3 The launcher option.** `--log-level <level>` applies to the server that command starts, including one the
bridge respawns, and overrides the environment variable and the setting. A server that is already running keeps
its level, and the launcher says the option was not applied and that a restart is needed.

**9.4 The rest of logging.** Already in the specs, with no further design: named loggers for the plugin that
write to the same file, format and level; stack traces for uncaught exceptions and unhandled rejections in the
launcher, the server and the bridge before a non-zero exit; a start line and an end line with the duration for
every tool call, made automatic by the `register` helper from Decision 4; and the debug mirror to standard error
from 6.9.

**Alternatives considered:** `winston` (its rotation module has had no release within the 12-month rule), `pino`
with a roll module (same finding); `rotating-file-stream` as a replacement if `log4js` ever has to go, behind the
same internal module.

### Decision 10: Testing

Each point was approved on its own.

**10.1 The test runner.** Node's built-in `node:test` with `node:assert`, run with `node --test` over a `test/`
folder. There is no test framework dependency and no build step.

**10.2 What is tested and how.** Two layers, and each test claims only what it checks. Unit tests cover the pure
pieces without processes: the argument parser, dates and relative dates, comma splitting and quoting, the
configuration merge, and the version compare. Real-process tests cover everything that involves a server, with
no mocks, because a mock of `spawn` and `http` would not show what actually breaks (ports, detached children,
files). A small stand-in MCP in `test/fixtures/`, written with the framework as an author would, is started as
a real detached server. These tests cover: start and the `/health` fields; a start while the same version runs;
replacing an older server and refusing to replace a newer one; a port held by another program; stop, graceful
and with the kill fallback; the bridge forwarding a message and recovering after the server is killed;
first-run and corrupt configuration; and the Origin and Host refusals and the 1 MB limit.

**10.3 Isolation.** Each test gets its own temporary folder and starts its processes with `HOME` and
`USERPROFILE` pointing at it (checked: `os.homedir()` follows `USERPROFILE` on Windows), so no special test
setting is needed in the framework and a test never touches the real `~/.mcp` or a running server. Each test
picks its own free port, writes it into that configuration, and stops its servers and deletes its folder even
when it fails.

**10.4 CI.** A `test.yml` that runs on push and pull request and can be called by the publish workflow, on
`ubuntu-latest` only, with Node 22 (the minimum supported) and Node 24 (as in the sibling repository). Steps:
`npm ci`, `npm audit fix`, `npm audit --audit-level=high`, `npm test`. Windows and macOS are not in CI: the
failures that matter are the broad, non-platform ones, and the developer runs `npm test` on Windows before a
release.

**10.5 The release checklist.** `RELEASING.md`, run before each release: `npm test` passes on the developer's
Windows machine; with the debug option the log lines appear in a real terminal window (6.9); the stand-in MCP,
registered with a real client over stdio and over HTTP, answers a tool call; and the README's integration steps,
followed exactly in a clean folder, produce a working MCP. The release tasks are the last steps in `tasks.md`.

**Alternatives considered:** a test framework such as Jest or Vitest (a dependency and, for Vitest, a build-style
configuration, for no gain over `node:test`); mocking `spawn` and `http` for the lifecycle tests; a Windows CI
job.

### Decision 11: Packaging and release

Each point was approved on its own.

**11.1 What ships.** The package is `@audaciousinquiry/mcp-framework`. Its `files` list is `src/`, `README.md` and
`LICENSE`; tests, fixtures, the OpenSpec folder, `RELEASING.md` and the CI files stay in the repository. `main`
points at the framework entry and `engines` requires Node 22 or later. `npm pack --dry-run` lists exactly what
would be published, so it can be checked.

**11.2 Versioning and the release workflow.** Follow the public sibling repository. Pushing a tag `vX.Y.Z` runs
`publish.yml`, which first calls `test.yml` and publishes only if the tests pass, with
`npm publish --access public --provenance` through npm's OIDC trusted publishing (`id-token: write`, no stored
npm token). One step is added from the other sibling's workflow: it fails when the tag's version does not match
`package.json`. Versions follow semver, and the bump itself is a decision for the user when implementation
starts. Before the first tag, the user adds a trusted publisher for this repository on npmjs.com (organization
`@audaciousinquiry`, publisher GitHub, owner `AudaciousInquiry`, repository `mcp-framework`, workflow
`.github/workflows/publish.yml`); the organization-level setting lets the first tagged release create the
package. The sibling's workflow still sets `NODE_AUTH_TOKEN` from `GITHUB_TOKEN` and publishes successfully, so
it is copied as is; if the first publish fails, that line is the first suspect.

**11.3 The Node version.** `engines` is only a warning in npm, so the launcher also checks the Node major version
before anything else. Below 22 it prints one clear line, such as "needs Node 22 or later, found 20", and exits
non-zero.

**11.4 The README integration guide.** In this order: what it is; a five-minute example of the three files
(`index.js`, `server.js`, `tools.js`) with start, call and registering with a client; the launcher definition and
the `ctx` object; writing tools with `defineTools` and `register`; the server class and when each method runs;
the command line; registering over stdio and over HTTP; configuration and logging; and the things worth
knowing (the pipe caveat from 6.9, defaults that change after first run, `/shutdown` as the only graceful stop on
Windows, the 1 MB limit and `maxBodyBytes`). The example is the same code as the stand-in MCP in `test/fixtures/`,
with the code blocks copied from those files so the guide cannot drift from what works.

**Alternatives considered:** an unscoped package name; a long-lived npm token stored as a repository secret;
publishing from a developer machine; a README example that is separate from the tested fixture.

## Risks / Trade-offs

- **Splitting each tool into a schema and a handler.** Authors move their schemas into the shared file. For
  an existing server with inline schemas, such as the ones the framework was extracted from, that is
  mechanical work for the migration change. Mitigation: the `register` helper keeps the split small, and the
  README shows the pattern.
- **Two files per MCP.** An author keeps a launcher and a server in step. Mitigation: the launcher is a few
  lines, `serverScript` defaults to the conventional name, and the launcher checks for the file at start-up.
- **Inheritance.** A base class couples authors to the framework's class shape. Mitigation: the overridable
  methods are the documented contract and follow the same semver rules as the rest of the public surface.
- **An unmaintained logging library.** `log4js` has had no release in over three years. Mitigation: the user
  approved it as an exception, `npm audit` is clean today, and only one internal module imports it, so
  `rotating-file-stream` can replace it without changing the public surface.
